# LLD.md — Low-Level Design

## 1. Conventions

- IDs: UUID v7 strings (time-sortable), generated by `IdGenerator`.
- Column names `snake_case` in SQLite, `camelCase` in TypeScript (Drizzle maps).
- Suffixes: `…M` = metres, `…Base` = base quantity units (mL / g / Wh), `…Minor` = currency minor units.
- Instants: UTC ISO-8601 text (`…At`). Calendar dates: `YYYY-MM-DD` text (`…Date`, `localDate`), computed in the user's time zone at entry.
- Every table has `created_at`, `updated_at`.
- Booleans as integer 0/1 (Drizzle `mode: 'boolean'`).

## 2. Database schema

### 2.1 Tables (DDL sketch — Drizzle schema in `src/db/schema.ts` is the source of truth)

```sql
create table vehicles (
  id               text primary key,
  name             text not null,                 -- "My Activa"
  type             text not null,                 -- bike | scooter | car | other
  fuel_type        text not null,                 -- petrol | diesel | cng | lpg | electric
  make             text, model text, year integer,
  plate            text,
  initial_odometer_m integer not null default 0,
  tank_capacity_base integer,                     -- optional; enables "fill > tank" warning
  is_archived      integer not null default 0,
  sort_order       integer not null default 0,
  created_at text not null, updated_at text not null
);

create table fill_ups (
  id               text primary key,
  vehicle_id       text not null references vehicles(id) on delete cascade,
  filled_at        text not null,                 -- UTC instant
  local_date       text not null,                 -- for monthly grouping
  odometer_m       integer not null,
  quantity_base    integer not null,              -- mL | g | Wh (by vehicle fuel_type)
  total_minor      integer not null,
  currency         text not null,                 -- ISO 4217, from settings at entry time
  is_full          integer not null default 1,
  missed_previous  integer not null default 0,
  entry_mode       text not null,                 -- qty_price | qty_total | price_total | amount_only
  station          text, note text,
  created_at text not null, updated_at text not null
);
create unique index fill_ups_vehicle_odo on fill_ups(vehicle_id, odometer_m);
create index fill_ups_vehicle_date on fill_ups(vehicle_id, local_date);

create table services (
  id               text primary key,
  vehicle_id       text not null references vehicles(id) on delete cascade,
  serviced_date    text not null,
  odometer_m       integer,                       -- optional
  type_key         text not null,                 -- preset key (KB §5) or 'custom'
  title            text,                          -- required when type_key = 'custom'
  cost_minor       integer, currency text,
  note             text,
  created_at text not null, updated_at text not null
);
create index services_vehicle_date on services(vehicle_id, serviced_date);

create table reminders (
  id               text primary key,
  vehicle_id       text references vehicles(id) on delete cascade,  -- null = person-level (licence)
  kind             text not null,                 -- service | document | custom
  type_key         text not null,                 -- preset key or 'custom'
  title            text,
  due_date         text,                          -- either or both of due_date / due_odometer_m
  due_odometer_m   integer,
  repeat_months    integer,
  repeat_distance_m integer,
  lead_days        integer not null default 7,
  lead_distance_m  integer not null default 300000,
  status           text not null default 'active', -- active | done | archived
  last_done_date   text, last_done_odometer_m integer,
  created_at text not null, updated_at text not null,
  check (due_date is not null or due_odometer_m is not null)
);
create index reminders_vehicle_status on reminders(vehicle_id, status);

create table odometer_readings (                  -- manual "update odometer" without a fill-up
  id text primary key,
  vehicle_id text not null references vehicles(id) on delete cascade,
  read_at text not null, local_date text not null,
  odometer_m integer not null,
  created_at text not null, updated_at text not null
);

create table settings (                           -- travels with backups
  key text primary key,                           -- language, region, currency, distance_unit, volume_unit,
  value text not null,                            -- efficiency_format_liquid, efficiency_format_ev, theme,
  updated_at text not null                        -- notify_weekly_nudge, current_vehicle_id
);
```

Device-only state (MMKV, not backed up): `ads.*` counters, `last_export_at`, `nudge.*`. Scheduled notifications need no stored ids: each carries its key in its data (ARCHITECTURE §4.3).

Vehicle edits (KB #24): with at least one fill-up, `fuel_type` may only change to a fuel with the same base unit (`baseUnitFor`: mL / g / Wh) and `initial_odometer_m` must stay ≤ the lowest fill-up `odometer_m`. Enforced in `VehicleService.update` via the `VehicleFillUpHistory` port (implemented by `FillUpService`) as `INVALID_VEHICLE` issues `fuel_locked` / `above_first_fill_up`.

Fill-up writes (`FillUpService`): field rules in `validateFillUp` (no instant > now + 5 min, total ≥ 0, quantity 1 base unit…1,000,000), order rules in `checkOdometerOrder` (FR-7 by `filled_at`, unique per vehicle, ≥ the vehicle's start). Odometer errors carry no readings (AGENTS.md rule 2); the form asks `odometerProblem()` for the reading to beat.

Services (`ServiceLogService`, migration `0002_services`): `serviced_date` is a calendar day and can't be after today; odometer and cost are optional, `currency` is stored only with a cost; a preset stores no `title` (its name follows the app language), `custom` needs one. A service odometer can't be below the vehicle's starting odometer but is not ordered against fill-ups (services are often logged later from a receipt). Readings from services count toward the current odometer (§5.1). History lists fill-ups and services together by month; the month header is everything spent (fuel + services), while the dashboard's monthly spend stays fuel only (§4.1 rule 8).

Reminders (`ReminderService`, migration `0003_reminders`): `kind` / `type_key` must match (service presets, document keys, `custom` with a title); only a `licence` may have no vehicle and is then date-only. Mark done defaults to today and the current odometer (an `OdometerSource` port wired in `container.ts`). Logging a service with a preset key completes that vehicle's active service reminders for the same key from the service's date and odometer; custom services never match.

Onboarding (KB #21): `onboarding_done` lives in the `settings` table, and the app counts onboarding as done when that flag is set **or** at least one vehicle exists — so an interrupted save or a restored backup without the flag never shows onboarding again. `current_vehicle_id` falls back to the first active vehicle when the saved one is missing or archived.

## 3. Units (`src/domain/units.ts`)

| Quantity    | Stored                       | Display options                                 |
| ----------- | ---------------------------- | ----------------------------------------------- |
| Distance    | metres (int)                 | km, mi (1 mi = 1609.344 m)                      |
| Liquid fuel | mL (int)                     | L, US gal (3785.411784 mL), UK gal (4546.09 mL) |
| CNG         | g (int)                      | kg                                              |
| Electric    | Wh (int)                     | kWh                                             |
| Money       | minor units (int) + ISO code | `Intl.NumberFormat(locale, {style:'currency'})` |

Efficiency formats:

| Format         | Formula (from distance m, quantity base) |
| -------------- | ---------------------------------------- |
| km/L           | (m/1000) / (mL/1000)                     |
| L/100km        | (mL/1000) / (m/1000) × 100               |
| mpg (US)       | (m/1609.344) / (mL/3785.411784)          |
| mpg (UK)       | (m/1609.344) / (mL/4546.09)              |
| km/kg (CNG)    | (m/1000) / (g/1000)                      |
| km/kWh, mi/kWh | distance / (Wh/1000)                     |
| kWh/100km      | (Wh/1000) / (m/1000) × 100               |

Rounding happens only for display (1 decimal for efficiency; currency's minor digits for money). Input parsing accepts both `.` and `,` decimal separators per locale.

**Region defaults** (`src/domain/regions.ts`): `IN` → INR, km, L, km/L, names PUC / RC / insurance; `US` → USD, mi, US gal, mpg US, names emissions/smog check, registration; `GB` → GBP, mi, L entry with mpg UK display, MOT, road tax; default → locale currency, km, L, L/100km, "emission test". Unknown regions fall back to default. EV display defaults: IN km/kWh, US and GB mi/kWh, default kWh/100km. CNG uses km/kg everywhere. Name strings live in `en.json`/`hi.json` under `regionNames.*`; `regions.ts` picks the key.

**User overrides** (Settings → Units, F-14): currency, distance unit, volume unit and the liquid/EV efficiency formats can each be changed; only changed fields are stored (`currency`, `distance_unit`, `volume_unit`, `efficiency_format_liquid`, `efficiency_format_ev`), the rest follow the region (`resolveUnits` in `src/domain/unit-preferences.ts`). Changing the region clears all unit overrides. Preference writes are queued so they apply in the order the user made them.

## 4. Efficiency engine (`src/domain/efficiency.ts`)

### 4.1 Rules

1. Order a vehicle's fill-ups by `odometer_m` ascending (unique per vehicle).
2. The first full fill-up is the **baseline**; fill-ups before it (or the very first entry) produce no efficiency.
3. A **segment** runs from one full fill-up (exclusive) to the next full fill-up (inclusive):
   - `distance = odo(endFull) − odo(startFull)`
   - `quantity = Σ quantity of every fill-up after startFull up to and including endFull` (partials included)
   - `cost = Σ total of the same fill-ups`
4. If any fill-up in the segment has `missed_previous = 1`, the segment is **invalid** (shown as "—, missed fill-up") and excluded from averages. The next segment starts from that segment's end full fill-up.
5. Partial fill-ups never get their own number; the UI shows "partial — included in next full tank".
6. **Average efficiency** = Σ distance ÷ Σ quantity over valid segments in the range (not the mean of segment values).
7. **Cost per distance** = Σ cost ÷ Σ distance over valid segments.
8. **Monthly spend** = Σ `total_minor` of fill-ups by `local_date` month — independent of segments.

### 4.2 Plausibility ranges (warn, not block — FR-8)

Bike 15–120 km/L, scooter 20–100 km/L, car 4–40 km/L, CNG car 10–40 km/kg, electric scooter 10–80 km/kWh, electric car 3–12 km/kWh. Also warn if a single fill-up quantity exceeds `tank_capacity_base` × 1.1.

Added 2026-10 (KB #20): CNG bike/scooter 40–120 km/kg; electric bike 10–80 km/kWh; type "other" 4–120 km/L, 10–120 km/kg, 3–80 km/kWh; LPG and diesel use the liquid ranges of their vehicle type. Bounds are inclusive; invalid or empty segments are never flagged.

### 4.3 API

```ts
type EfficiencyFillUp = { id; odometerM; quantityBase; totalMinor; currency; isFull; missedPrevious; localDate };
interface Segment {
  startId: string; // full fill-up the segment starts after (exclusive)
  endId: string; // full fill-up that closes it (inclusive)
  endDate: string; // localDate of the closing fill-up — segments belong to the period they close in
  distanceM: number;
  quantityBase: number;
  costs: Money[]; // per currency (one entry unless the user changed currency mid-segment)
  valid: boolean;
  reason?: 'missed_fill';
}
class EfficiencyEngine {
  segments(fillUps: EfficiencyFillUp[]): Segment[]; // sorts by odometer itself (fixture #7)
  summary(segments, range?: { from?: string; to?: string }): {
    distanceM; quantityBase; validSegments; costs: { cost: Money; distanceM }[];
  };
  value(totals: { distanceM; quantityBase }, format: EfficiencyFormat): number | null; // LLD §3 formulas
  costPerDistance(cost: { cost: Money; distanceM }, unit: 'km' | 'mi'): Money | null;
}
quantityFromTotal(total: Money, unitPrice, unit): number | null; // amount-only (src/domain/fill-up.ts)
```

- `range` filters valid segments by `endDate` (inclusive); average = Σ distance ÷ Σ quantity of those segments.
- Cost per distance is per currency and never adds currencies (KB §3); a segment that mixes currencies counts for efficiency but is left out of cost per distance.
- `value` returns null when distance or quantity is 0, so the UI shows "—" instead of a number.
- `plausibility(segment, { type, fuelType }) → 'ok' | 'too_high' | 'too_low'` and `exceedsTank(quantityBase, tankCapacityBase)` implement §4.2.
- Before saving, `FillUpService.warnings(input, editingId)` runs the engine on the vehicle's entries as they would be after the save and checks the segments that end or start at the new entry, plus `exceedsTank`. The entry form shows them in one dialog (Check again / Save anyway); nothing is blocked.

## 5. Reminder planning (`src/domain/reminder-planner.ts`, `distance-forecaster.ts`)

### 5.1 Current odometer

`max(latest fill_up.odometer_m, latest services.odometer_m, latest odometer_readings.odometer_m, vehicles.initial_odometer_m)`.

### 5.2 Distance forecast

- Use readings (fill-ups, services with an odometer, and manual odometer readings once they exist) from the last 90 days.
- Needs ≥ 2 readings spanning ≥ 7 days; otherwise no forecast.
- `avgDailyM = (lastOdo − firstOdo) / daysBetween`.
- Predicted date for a distance-due reminder: `today + ceil((dueOdo − currentOdo) / avgDailyM)` days; if `avgDailyM` = 0 → no forecast. The UI says "Around <date>" when the effective date comes from the forecast.

### 5.3 Effective due

- Date-only → `due_date`. Distance-only → predicted date (if any). Both → the **earlier** of the two.
- States: `upcoming` (beyond lead), `due_soon` (within lead days or lead distance), `due` (today / odometer reached), `overdue`.

### 5.4 Desired notifications

For each active reminder with an effective due date: one at 09:00 on `due − lead_days` (if in future), one at 09:00 on due day, one "overdue" 3 days after. Weekly nudge (if enabled and no entry in 7 days): Sunday 10:00. Monthly backup nudge is in-app only. Sort by fire time; keep first 60.

Permission is asked when the user saves a reminder while the OS still allows a prompt (AGENTS.md rule 13), never at launch. Distance reminders without a forecast and reminders of archived vehicles are not scheduled. Tapping a notification opens the Reminders tab.

### 5.5 Completing a reminder

On done (or matching service logged): set `last_done_*`; if `repeat_months` / `repeat_distance_m` set → advance `due_date` by months from done date and `due_odometer_m` by distance from done odometer; else `status = done`.

## 7. Backup file format

```json
{
  "app": "fuelora",
  "schemaVersion": 1,
  "exportedAt": "2026-10-27T10:00:00Z",
  "appVersion": "1.0.0",
  "data": {
    "vehicles": [ … ], "fillUps": [ … ], "services": [ … ],
    "reminders": [ … ], "odometerReadings": [ … ], "settings": [ … ]
  }
}
```

- Rows use the same camelCase fields as the Drizzle types (canonical units).
- File name `fuelora-backup-YYYY-MM-DD.fuelora` (JSON content; MIME `application/json`). Registered as a document type so other apps offer "Open in Fuelora" (FR-23). Import also accepts `.json`.
- Import: validate with Zod → migrate `schemaVersion` n → current step by step (`backup-migrations.ts`) → replace all in one transaction.
- CSV export: one file per vehicle with display units and a header row; not importable in MVP.

## 9. Error model

`AppError(code, message, details)`; codes in `src/domain/errors.ts`: `ODOMETER_NOT_INCREASING`, `ODOMETER_AFTER_NEXT`, `DUPLICATE_ODOMETER`, `ODOMETER_BELOW_START` (below the vehicle's starting odometer), `INVALID_FILL_UP` (field issues in `details.issues`, like `INVALID_VEHICLE`; replaces the planned `MISSING_FILL_FIELDS` / `INVALID_NUMBER`), `FILL_UP_NOT_FOUND`, `REMINDER_NEEDS_DUE`, `BACKUP_INVALID_FILE`, `BACKUP_NEWER_VERSION`, `NOTIFICATION_PERMISSION_DENIED`. Screens map codes to `errors.<code>` i18n keys.
